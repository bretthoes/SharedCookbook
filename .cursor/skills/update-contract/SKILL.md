# Updating a Contract DTO

## ⚠️ Breaking change assessment

**Before making any edits**, classify the change and warn the user if it is breaking.

| Change type | Breaking? | Why |
|-------------|-----------|-----|
| Add nullable property to a response DTO (`RecipeBriefDto`, `RecipeDetailedDto`) | **No** — old clients ignore unknown fields | Safe to add |
| Add nullable property to a request DTO (`RecipeDto` base, `CreateRecipeDto`, `UpdateRecipeDto`) | **No** — server treats missing fields as `null` | Safe to add |
| Rename or remove a property from any DTO | **Yes** — old clients sending the old name will silently lose data; old clients reading the old name will get `null` | Warn user |
| Change a property type (e.g. `string` → `int`) | **Yes** — old clients will fail to deserialize | Warn user |
| Make a previously nullable property required | **Yes** — old clients that omit it will fail validation | Warn user |

If the change is breaking, tell the user before proceeding:

> ⚠️ **This is a breaking API change.** Old versions of cookbook-mobile that haven't been updated will [describe the impact]. Consider a versioned endpoint or a phased rollout if clients in the wild may not be updated atomically.

## Project layout

| Path | Purpose |
|------|---------|
| `src/Application/Contracts/` | All DTO classes |
| `src/Application/Common/Mappings/` | LINQ projections from entities → DTOs |
| `src/Application/Recipes/Queries/` | DB query helpers that project DTOs inline |
| `src/Web/wwwroot/api/specification.json` | Auto-generated by NSwag on Debug build |

## Workflow

```
- [ ] Step 1: Edit the DTO
- [ ] Step 2: Update projection(s)
- [ ] Step 3: Build Web project (regenerates spec)
- [ ] Step 4: Verify
```

---

### Step 1: Edit the DTO

Modify the relevant file in `src/Application/Contracts/`.

**Conventions:**
- Records use `init`-only properties: `public bool? IsVegetarian { get; init; }`
- Nullable types for all optional fields
- No data annotations — these are pure data transfer objects

**Which DTO to edit:**

| DTO | Used for |
|-----|---------|
| `RecipeBriefDto` | List/paginated responses |
| `RecipeDto` (abstract base) | Create and Update request bodies |
| `RecipeDetailedDto` | Single-recipe GET response |
| `CreateRecipeDto` | Inherits `RecipeDto`; adds `CookbookId` |
| `UpdateRecipeDto` | Inherits `RecipeDto`; adds `Id` |

---

### Step 2: Update Projections

After editing a DTO, find all places that project into it and add the new fields.

**For `RecipeBriefDto`** — update `ToBriefDto` in:
`src/Application/Recipes/Queries/GetRecipesWithPagination/GetRecipesDbQuery.cs`

**For `RecipeDetailedDto`** — update `ToDetailedDto` in:
`src/Application/Common/Mappings/RecipeMapping.cs`

**For `RecipeDto` (base)** — update the command handlers:
- `src/Application/Recipes/Commands/CreateRecipe/CreateRecipe.cs`
- `src/Application/Recipes/Commands/UpdateRecipe/UpdateRecipe.cs`

To find all projection sites for any DTO:

```powershell
rg "new RecipeBriefDto" src/
```

Replace `RecipeBriefDto` with the name of the DTO you changed.

---

### Step 3: Build the Web Project

Run from the repo root (PowerShell):

```powershell
dotnet build src/Web --configuration Debug
```

This triggers the NSwag post-build target which regenerates `specification.json`.

> **Build must be `Debug` configuration** — the NSwag target only runs when `Configuration == 'Debug'`. Release builds skip it.

> **If NSwag fails** with a database error: the `ApplicationDbContextInitialiser` runs at startup. Ensure `src/Web/appsettings.Development.json` has a valid connection string, or check `src/Web/appsettings.json` for defaults. NSwag invokes the app at design time.

Confirm success: build output should contain `Executing file 'config.nswag'...` and end with `Build succeeded`.

---

### Step 4: Verify

- [ ] New properties appear in `src/Web/wwwroot/api/specification.json`
- [ ] All projection sites compile without errors (confirmed by Step 3 build)
